# didwebvh-py crashes with AttributeError when a did:key body and fragment disagree
kind: todo
created: 2026-09-15T23:13Z

- 2026-09-15T23:13Z Second upstream defect in decentralized-identity/didwebvh-py at pin 905f5e1, after ~2qhs (the empty-log hang). Found by DIF's own conformance vector negative-did-key-body-fragment-mismatch.

core/proof.py resolve_did_key() raises a bare ValueError when a proof's verificationMethod names a did:key whose body and fragment are different keys. state.py verify_state_proofs() calls it OUTSIDE the try/except ValueError that wraps the actual proof check, so that ValueError escapes as-is; something upstream of it then reads .problem_details and the caller sees AttributeError: 'ValueError' object has no attribute 'problem_details'.

Minimal repro, library code only, no didwebvh involved: feed the vector's did.jsonl to DidResolver.resolve via read_str. Confirmed 2026-09-15.

FAILS CLOSED -- the log is refused, not accepted -- so this is error attribution rather than a vulnerability. The vector's scenario is an attacker signing with their own key while naming an authorized key in the did:key body, and the library does reject it. What it cannot do is say so.

Impact here: an invalid submission surfaced to the customer as e.self.unknown.f, 'this service failed in a way it does not recognize, please report it'. Their log is bad and we told them it was our fault. Worked around in verify.py by mapping non-BakoboError exceptions out of the library's walk onto e.proof.log.undiagnosed.f, which says the log failed and that the diagnosis is imprecise.

Report to DIF alongside ~2qhs; both are in the same file and the same fix session would cover them.
